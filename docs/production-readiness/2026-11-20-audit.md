## Production blockers

### P0/P1 — migration drift and missing production objects

- Supabase migration history: 98 applied versions.
- Current `develop` repository: 43 SQL migration files.
- 55 applied migration files are absent from the current repository.
- 11 migration files in `develop` are not recorded as applied in production.
- The unapplied migrations include functions currently called by Worker code: `confirm_prospect_review`, `promote_prospect_to_lead`, `finalize_prospect_contact_conversion`, and `inbox_claim_media_jobs`.
- Production does not currently contain `public.inbox_attachments` or `public.inbox_media_jobs`, although Worker routes and the scheduled media processor depend on them.
- The `avatars` bucket and its four owner-scoped storage policies are present despite the matching migration not appearing in migration history; this is an example of schema/history drift.
- Do not apply the 11 pending migrations blindly. Restore/reconcile the missing migration source history first, then validate the pending migrations in an isolated environment before any production schema change.

### P1 — Agent runtime and configuration

- Production contains three Agent profiles: `buyer_development` enabled; `company_research` and `lead_scoring` disabled. Recent failed runs with `AGENT_DISABLED` are consistent with this configuration and were not auto-enabled.
- Ten built-in registry tools are currently enabled; all ten are read-only. No external Agent connections or saved workflows were found. User configuration was not changed.
- One historical Agent run had no matching Cloudflare Workflow instance and was reconciled to failed.
- Agent queue recovery, stale-run monitoring and end-to-end execution still need verification.

### P1 — release governance and provenance

- GitHub `develop` branch protection is currently disabled.
- The current `deploy.yml` in `develop` is manual-only and defaults to `hold`, which is the intended release gate.
- Cloudflare currently routes 100% of the `tradepilot` Worker deployment to version 812. Its deployment metadata does not contain a Git commit SHA, so the deployed artifact cannot yet be conclusively tied to the audited `develop` commit.
- No production deployment was initiated as part of this audit.

### P1 — authentication and security configuration

- Supabase Auth leaked-password protection is disabled and needs to be enabled before production sign-off.
- Supabase security advisor warns about five authenticated SECURITY DEFINER functions. Cross-owner denial tests passed, but these functions remain documented exceptions that must be retained in the security review.
- Performance advisor reports four duplicate-index pairs, 52 unindexed foreign keys and four RLS init-plan warnings. These require query-aware remediation; no indexes were removed in this audit.

## Environment constraints

- A Supabase development branch was not created because the quoted compute cost is USD 0.01344/hour. No paid staging resources were started.
- Automated browser/E2E acceptance has not yet been performed. CI success is not a substitute for real production browser verification.

## Release decision

**HOLD — not production-ready for final sign-off.**

Required before release:
1. Restore/reconcile migration history and verify every Worker RPC/table dependency.
2. Validate and apply the pending schema changes in a safe test environment.
3. Enable leaked-password protection and close/accept security advisor findings.
4. Add branch protection and require successful CI before merge.
5. Establish an auditable Git SHA → Worker version deployment record.
6. Complete business-flow, tenant-isolation, Agent execution, recovery, and real-browser E2E acceptance.
7. Only then use the manual production workflow with explicit release approval.
